# ARTCB — DIRECTIVE GLOBALE DE DÉVELOPPEMENT ET D’AUDIT

## PRIORITÉ ABSOLUE : LANGAGE IA-ARTCB

### 0. Règle générale de travail

À partir de maintenant, **le développement du langage IA-ARTCB devient la priorité absolue du projet**.

Cela ne signifie **en aucun cas** que les autres chantiers doivent être arrêtés, oubliés ou mis en pause.

Tous les chantiers doivent continuer **simultanément et en parallèle**, avec une gestion explicite des dépendances.

L'ordre de priorité est donc :

1. **Langage IA-ARTCB**
2. Identité / HumanID / biométrie / anti-Sybil
3. PoL / KnowledgeID / UsageID / WorkID
4. Jobs / Provider / Worker / priorité
5. Économie / monétisation / frais / settlement
6. Public / privé / ORG / GROUP / provenance
7. Blockchain / consensus / infrastructure
8. Tests / simulations / sécurité / certification
9. Nouveaux modules linguistiques et nouvelles capacités IA

Aucun chantier précédent ne doit être abandonné simplement parce qu'un nouveau chantier devient prioritaire.

---

# 1. OBJECTIF FONDAMENTAL : ARTCB EST UN SYSTÈME CONÇU POUR LES IA ET LES AGENTS

ARTCB doit être conçu prioritairement comme une infrastructure destinée aux :

* IA ;
* agents autonomes ;
* agents logiciels ;
* machines ;
* systèmes d'IA coopératifs ;
* échanges de connaissances entre agents ;
* production et validation de raisonnements ;
* Proof of Learning ;
* traçabilité des travaux ;
* réutilisation de connaissances.

L'utilisateur humain reste nécessaire pour certaines fonctions d'identité, de validation ou de gouvernance, mais **le produit principal n'est pas un réseau social humain**.

La matière première d'ARTCB est :

```text
IA
↓
travail
↓
raisonnement
↓
connaissance
↓
utilisation
↓
preuve
↓
validation
↓
valeur
```

Les anciens rapports ont déjà défini cette séparation entre langage IA, raisonnement, travail, PoL, KnowledgeID et blockchain.

---

# 2. LANGAGE IA-ARTCB : PRIORITÉ P0 ABSOLUE

## 2.1 Objectif

Je veux maintenant que le langage IA-ARTCB soit développé jusqu'à **100 % de la bibliothèque lexicale définie pour les 14 langues initiales du projet**.

Il ne faut pas produire uniquement :

* quelques phrases ;
* quelques exemples ;
* quelques concepts ;
* quelques milliers de mots ;
* un vocabulaire de démonstration.

L'objectif demandé est la **bibliothèque complète définie pour chacune des 14 langues initiales**.

Aucune des 14 langues ne doit être abandonnée.

Aucune langue ne doit être considérée comme « suffisamment couverte » simplement parce que quelques phrases convergent correctement.

* dans un sous-groupe ;
* sur une machine appartenant à l'organisation ;

ne doit pas supprimer la provenance de son producteur.

---

# 27. ORGANISATION ≠ PROPRIÉTAIRE AUTOMATIQUE DU RAISONNEMENT

Il faut donc distinguer :

```text
Producer
Author
HumanID
AgentID
MachineID
OrganizationID
GroupID
JobID
KnowledgeID
```

Ces identités ne doivent pas être fusionnées.

Une organisation peut avoir des droits sur un raisonnement selon ses règles contractuelles et son architecture privée, mais cela ne doit pas supprimer l'information de provenance :

```text
ProducedBy = X
```

---

# 28. PUBLICATION D'UN RAISONNEMENT PRIVÉ

Si une organisation décide qu'un raisonnement privé doit être rendu public :

```text
raisonnement privé
       ↓
sélection
       ↓
publication / export public
       ↓
validation publique
       ↓
preuve d'utilité
       ↓
récompense publique éventuelle
```

La récompense publique doit être attribuée selon les règles du protocole à la contribution réellement éligible, avec conservation de la provenance.

Le simple fait qu'une organisation publie le raisonnement ne doit pas automatiquement transformer :

```text
OrganizationID
```

en :

```text
ProducerID
```

si le producteur réel est un autre agent/utilisateur.

---

# 29. CONFIDENTIALITÉ : LE CONTENU PRIVÉ NE DOIT PAS ÊTRE OBLIGATOIREMENT PUBLIÉ

Il faut prévoir une architecture :

```text
contenu privé
      ↓
hash / commitment
      ↓
preuve publique
```

afin que le réseau public puisse éventuellement vérifier :

```text
ce raisonnement existait
+
il n'a pas été modifié
+
il possède telle provenance
+
il possède telle preuve
```

sans obligatoirement publier le raisonnement confidentiel lui-même.

Les anciens travaux ont déjà identifié cette architecture « confidentialité + vérifiabilité ».

---

# 30. VALORISATION PUBLIQUE DU RAISONNEMENT

Dans le privé :

```text
raisonnement
↓
valeur estimée
```

Cette estimation ne doit pas être présentée comme une récompense publique définitivement acquise.

Lorsqu'un raisonnement passe dans le public :

```text
PRIVATE KNOWLEDGE
      ↓
PUBLIC CANDIDATE
      ↓
validation
      ↓
Utility Evidence
      ↓
Public Knowledge
      ↓
reward éventuelle
```

La valeur économique publique doit dépendre des règles publiques de validation et de récompense.

---

# 31. NE PAS CONFONDRE « ESTIMATION » ET « SOLDE »

Si le système affiche :

```text
Estimation = X €
```

cela ne signifie pas nécessairement :

```text
Solde disponible = X €
```

Il faut donc avoir des états explicites :

```text
EstimatedValue
PendingReward
ValidatedReward
SettledReward
LockedReward
AvailableBalance
```

C'est particulièrement important avec le système de règlement mensuel et de lock déjà défini dans les travaux précédents.

---

# 32. TRAÇABILITÉ IDENTIQUE PUBLIC / PRIVÉ

Le traitement doit rester conceptuellement identique :

```text
PRIVATE
```

et

```text
PUBLIC
```

doivent utiliser la même logique fondamentale de :

```text
identification
+
provenance
+
WorkID
+
KnowledgeID
+
UsageID
+
validation
+
historique
```

La différence fondamentale est :

```text
VISIBILITÉ
+
AUTORISATION
+
RÈGLE ÉCONOMIQUE
+
PUBLICATION
```

et non :

```text
privé = aucune traçabilité
```

---

# 33. CHANTIER À AJOUTER : TRANSITION PRIVATE → PUBLIC

Créer un chantier spécifique pour formaliser :

```text
PrivateKnowledgePublication
```

Il doit définir :

1. qui peut publier ;
2. qui peut demander la publication ;
3. si le producteur doit consentir ;
4. si l'organisation peut publier ;
5. quelles métadonnées deviennent publiques ;
6. quelles données restent privées ;
7. comment est calculé le hash ;
8. comment est conservée la provenance ;
9. comment la récompense est attribuée ;
10. comment éviter qu'une même connaissance soit publiée plusieurs fois ;
11. comment gérer les versions ;
12. comment gérer les dérivations d'un raisonnement.

## OBJECTIF FINAL

ARTCB doit devenir une infrastructure dans laquelle :

**les IA peuvent communiquer, comprendre des concepts indépendamment de la langue humaine, produire des raisonnements, réutiliser les raisonnements d'autres agents, prouver leur travail, faire valider l'utilité de ce travail, conserver la provenance de chaque contribution, travailler dans des espaces privés ou publics, puis éventuellement transformer une connaissance privée en contribution publique vérifiable et rémunérable.**

Le développement doit donc maintenant être organisé autour de cette architecture complète, et non autour de fonctionnalités isolées.

**Aucune des 14 langues initiales ne doit être abandonnée. Aucun chantier déjà engagé ne doit être oublié. Aucun mécanisme documenté ne doit être considéré comme implémenté tant que le code réel et les tests ne le démontrent pas.**
