## 2. Qu’est-ce que `/p2p/sync` ? (la route qui renvoyait 500)

**P2P** = *peer-to-peer*, c’est-à-dire « de voisin à voisin », comme des voisins qui se passent des photocopies **sans** passer par une mairie centrale.

**`/p2p/sync`** = le bouton « mets-toi à jour avec tes voisins ». Il fait **deux** gestes :

1. **PULL** (tirer) — « donne-moi tes pages publiques ». C’est un simple listing. C’est **ce chemin** qui a fait converger OVH4 à height 3.
2. **PUSH** (pousser) — « tiens, je t’envoie *mes* pages, **dans une enveloppe verrouillée** ».

Comparer : le PULL est une carte postale lisible (blocs **publics** seulement). Le PUSH est un colis avec un cadenas dont seule la clé du destinataire ouvre.

**HTTP 500** = « le serveur a planté en coulisse ». Ce n’est **pas** « le destinataire a refusé » (ça serait 4xx). C’est le serveur qui **trébuche** avant de finir sa phrase.

## 3. Diagnostic : ce n’était pas une course, c’était une clé trop courte

Reproduit **à la demande**, deux fois de plus : toujours HTTP 500, même traceback.

Journal OVH4 (extrait utile) :

```text
POST /api/v1/p2p/sync  →  500
RuntimeError: Can not encapsulate secret
  dans push_to_peer → encrypt_payload
```

**Encapsulate** = fabriquer le cadenas ML-KEM.  
**ML-KEM-768** = le cadenas post-quantique du *transport* (FIPS 203). À ne pas confondre avec **ML-DSA-65**, qui est le *tampon de signature* (FIPS 204). C’est comme : cadenas de la porte (KEM) vs signature sur le contrat (DSA).

Taille attendue de la **clé publique** ML-KEM-768 : **1184 octets**.  
Taille trouvée pour AWS3 **avant** correctif : **32 octets**.

32 octets, c’est la taille d’une clé **X25519** — c’est-à-dire l’ancien *plan B* classique, comme un cadenas de vélo alors qu’on croit utiliser un coffre-fort de banque.

AWS3 **disait** `kem_algorithm = ML-KEM-768` (slogan) tout en **publiant** une clé de 32 octets (réalité). C’est un menteur involontaire : l’identité P2P avait été créée **avant** que liboqs (la bibliothèque PQC) soit vraiment là, puis on a installé liboqs **sans régénérer** la clé.

Donc le 500 était **à la fois** :

| Hypothèse expert | Verdict |
|------------------|---------|
| Bug reproductible | **Oui** — 3 fois avant correctif |
| Chemin secondaire redondant | **Oui** — le PUSH ; le PULL suffisait déjà à copier les blocs publics |
| Incompatibilité de chemin | **Oui** — cadenas ML-KEM vs clé X25519 |
| Erreur de données | **Oui** — clé stockée trop courte |
| Condition de course | **Non** — pas un timing ; la clé était fausse en permanence |

La convergence PRE-DV-04 **ne dépendait pas** du PUSH. Elle dépendait du PULL. C’est pour ça que le tip était bon **malgré** le 500. Ce n’était **pas** un succès silencieux de la couche sync complète.

## 4. Correctif (trois couches, comme une ceinture + bretelles + étiquette honnête)

1. **Ne plus planter toute la route** si *un* voisin a une mauvaise clé. On note `ok: false` pour ce voisin, HTTP **200** pour la route. Comparer : un facteur qui rentre quand même au dépôt après qu’une boîte aux lettres soit rouillée, au lieu de mettre le feu au camion.
2. **Dire la vérité** : `kem_algorithm` est déduit de la **taille** de la clé, pas d’un texte en dur.
3. **Mettre à jour l’identité** au redémarrage si liboqs est là et que la clé fait encore 32 octets. AWS3 est passé à 1184 octets.

Puis on a **effacé** l’ancien voisin AWS3 (32 octets) dans le carnet d’OVH4. Sans ça, le PUSH vers *ce fantôme* échouait encore — honnêtement, en 200, plus en 500.

## 6. Rotation des secrets collés dans le chat

Trois niveaux, comme l’expert :

| Niveau | Exemple | Faut-il tourner ? |
|--------|---------|-------------------|
| 1. Secret exposé | jeton Doppler `dp.st…`, Application Secret OVH, Consumer Key | **Oui** |
| 2. Secret copiable | même famille, si quelqu’un a scrollé le chat | **Oui** |
| 3. Identifiant public | IP `91.134.45.8`, id instance, slug `artcb-4`, nic `xy4589-ovh` | Non |

**État réel de la rotation :** **non terminée**. Le jeton Doppler du nœud 4 peut lire `/v3/me` mais **ne peut pas** créer un nouveau jeton de service (API workplace). Une nouvelle Consumer Key OVH exige un clic humain sur une URL de validation. L’Application Secret OVH ne se change pas : on crée une **nouvelle application** dans le manager OVH.

Donc : les clés chat restent **compromises**. L’accès actuel est prouvé ; l’**invalidation** des anciennes valeurs attend l’opérateur (Doppler UI + OVH console). Ne pas les recoller dans un prochain message.
